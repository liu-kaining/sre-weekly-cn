# 08｜生产发布、流量与上线验证

[返回阅读入口](README.md) · [下一章：运行态](09-runtime-and-reliability.md)

## 1. 输入、产出与重点

输入是明确的候选制品、配置、验证证据、发布策略和授权；产出是经过生产观察的版本，以及完整的发布过程记录。

部署完成意味着软件已按定义运行；生产发布还需要决定哪些用户使用新版本、怎样观察、什么时候扩大、何时停止。功能开关又可以独立决定功能是否对用户开放。

## 2. 谁负责

发布负责人确认本次变更范围、操作节奏与异常决策。业务开发保证实现与兼容，测试提供验证证据，SRE 协助运行风险和故障处置，平台团队提供发布编排与控制能力。

这些职责可以由不同岗位或同一人承担。发布前需要明确：谁有权暂停、回退和恢复，异常找谁，多久升级。

## 3. 常见发布策略

| 策略 | 实际动作 | 适合认识的优点 | 要承担的约束 |
|---|---|---|---|
| 滚动更新 | 逐批替换实例 | 复用现有部署机制 | 新旧版本共存，需要兼容和容量余量 |
| 蓝绿 | 同时准备两组版本，再切换入口 | 流量切换边界清晰 | 额外资源、连接与数据兼容 |
| 金丝雀／灰度 | 先给新版本部分流量或用户，再逐步扩大 | 在较小范围观察风险 | 需要分组、路由、观察和停止规则 |
| 功能开关 | 控制已部署代码中的功能入口 | 可以分别控制部署和功能开放 | 需要管理权限、默认值、失效及过期清理 |

这些机制可以组合。功能开关关闭后，已经写入的数据、发出的消息和执行过的迁移仍然存在，需要另外处理。

Kubernetes Deployment 支持滚动更新；更细的灰度策略可参考 [Argo Rollouts](https://argoproj.github.io/argo-rollouts/)。按请求分配权重需要相应流量管理能力，不能简单把“1 个新 Pod、9 个旧 Pod”等同于精确的 10% 请求，见 [流量管理说明](https://argoproj.github.io/argo-rollouts/features/traffic-management/)。

## 4. 一次生产发布应该经过哪些判断

### 发布前

- 固定制品摘要、部署定义、配置、目标环境和策略版本。
- 核对测试、风险例外、审批和依赖状态。
- 确认数据库变更顺序和旧版本兼容范围。
- 准备新旧版本观测、冒烟和恢复操作。
- 确认资源、值班和变更冲突。

审批应该对应具体输入。审批后替换镜像或关键配置，需要重新判断原审批是否仍适用。

### 发布中

1. 建立新版本实例，确认启动和就绪。
2. 从实际业务入口执行冒烟。
3. 按策略引入目标流量。
4. 观察新旧版本及共享依赖，判断继续、暂停或停止。
5. 扩大范围，直到完成约定的发布阶段。

### 发布后

确认版本分布与配置，保留观察窗口、发布记录及异常关联。流水线退出后仍要持续监控，不能只看发布那几分钟。

## 5. 本案例的教学灰度规则

以下为练习方案，数值用于帮助理解，不是通用生产标准：

| 项目 | 教学约定 |
|---|---|
| 阶段 | 测试 → 预发 → 小流量 → 扩大 → 全量 |
| 冒烟 | 合法用户可查、空结果正确、跨用户被阻止 |
| 新版观测 | 对 `/orders` 按版本观察失败率、P95、流量和数据库耗时 |
| 绝对目标 | 示例：有效请求成功率至少 99.9%，P95 小于 300ms |
| 相对比较 | 与同一窗口的旧版本对照，并解释请求构成差异 |
| 样本要求 | 示例：每阶段至少观察 5 分钟，且新版本有至少 1000 个有效请求 |
| 证据不足 | 未达到样本量或关键指标缺失时，继续等待或人工判断 |
| 异常动作 | 停止扩大，评估切回旧版本、关闭功能或其他止损方式 |

这些条件需要结合使用。刚好 1000 次请求时，极少的失败就会显著影响比例；少量样本也难以稳定估计尾延迟。演练阈值不能直接复制成生产规则。

自动分析至少区分“通过、失败、结果不确定”。监控查询错误、没有流量和没有错误请求是不同情况。[Argo Rollouts Analysis](https://argoproj.github.io/argo-rollouts/features/analysis/)提供指标分析及相应控制机制，具体模板需要按实际指标设置。

## 6. 数据库变更为什么是发布难点

应用可以切回旧镜像，数据库和用户数据未必能恢复原样。

对新增字段或格式调整，可研究“先扩展、再迁移、最后收缩”的兼容策略：

```text
增加兼容结构
  → 部署兼容新旧结构的代码
  → 分批迁移或补齐数据
  → 验证新读写路径
  → 经过兼容窗口后再删除旧结构
```

新增索引也要评估数据库版本、锁、磁盘和运行影响；“只加索引”不能自动视作无风险操作。本案例可以把索引变更作为独立任务，记录执行结果，再部署查询代码。

迁移任务应有唯一版本、执行记录和并发保护。执行超时后先检查真实状态，不能直接重复做非幂等变更。

## 7. 回滚、终止和修复要分别表达

| 操作 | 目的 | 需要确认 |
|---|---|---|
| 暂停 | 暂停后续推进，便于判断 | 当前流量、实例和观察是否仍受控 |
| 终止灰度 | 停止本轮新版本扩散 | 实际流量是否切回、后台控制器是否继续动作 |
| 应用回退 | 运行旧制品或旧配置 | 与当前数据库、消息和依赖是否兼容 |
| 关闭功能 | 停用特定用户入口 | 是否真的覆盖所有入口及副作用 |
| 前向修复 | 发布修正版解决问题 | 修复风险、验证与完成时间 |

回退是一项需要验证结果的操作。平台至少记录目标版本、路由和实例状态，再执行必要业务检查。

GitOps 模式还要处理 Git 中的期望状态。[Argo CD 自动同步文档](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/)说明启用自动同步时的回退限制，不能把历史回退按钮当作所有场景下都可直接执行的方案。

## 8. 平台后端的典型开发任务

发布平台可以采用以下教学状态：

```text
DRAFT → VALIDATING → APPROVAL_PENDING → READY
  → DEPLOYING → VERIFYING → CANARY → OBSERVING → SUCCEEDED
```

异常与控制分支包括 `PAUSED`、`ABORTING`、`ROLLING_BACK`、`ROLLED_BACK` 和 `FAILED`。每个状态要写清进入条件、允许动作、超时和外部系统状态。

关键实现包括：

- 审批绑定输入快照，变更后重新校验。
- 同环境发布互斥，防止两个任务交叉推进。
- 指标查询与判断规则版本化，记录窗口、样本和结果。
- 重复或迟到的回调不能覆盖更新状态。
- 平台重启后，基于执行步骤和外部状态恢复。
- 终止或回退期间，停止旧的自动推进任务。
- 所有操作保存身份、原因、输入、结果和关联 ID。

## 9. 技术栈与代表性开源项目

| 项目 | 适用能力 |
|---|---|
| [Argo Rollouts](https://argoproj.github.io/argo-rollouts/features/analysis/) | 渐进发布、分析与策略推进 |
| [Apache APISIX](https://apisix.apache.org/docs/apisix/getting-started/README/) | 网关与路由能力；具体灰度方式需配置验证 |
| [Unleash](https://docs.getunleash.io/) | 功能开关；需区分开源与商业能力 |
| [Kubernetes Deployment](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/) | 副本与滚动更新 |

不需要为了学发布而先搭建服务网格。先用一种可解释的方式控制流量，并验证它确实按预期生效。

## 10. 核心技能与案例验收

| 深度 | 本章应掌握 |
|---|---|
| 理解 | 部署、放量、开关、数据库变更和回退的不同边界 |
| 使用 | 做一次分批发布，检查新旧版本，主动暂停并验证恢复 |
| 开发平台 | 发布状态机、审批快照、互斥、指标判定、恢复和审计 |

本案例故意引入查询延迟，观察灰度是否停止。切回旧版本后，从业务入口验证恢复，记录故障与操作时间。

自测：所有 Pod 都 Ready，但新版本查询慢了三倍，平台应该根据什么决定暂停？监控服务恰好不可用时又怎么办？
