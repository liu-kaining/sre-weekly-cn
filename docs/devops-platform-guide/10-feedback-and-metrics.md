# 10｜反馈、复盘与研发效能度量

[返回阅读入口](README.md) · [下一章：平台后端研发](11-platform-backend-engineering.md)

## 1. 输入、产出与重点

输入是需求、代码、测试、构建、部署和运行事件，以及开发者反馈；产出是明确的瓶颈、改进任务和效果验证。

平台的价值需要同时看交付速度、质量、使用体验和运行成本。流水线数量增加、页面访问量提高，只能说明活动或采用情况，不能单独证明交付变好。

## 2. 谁负责

业务与平台负责人共同确定改进目标。开发、测试和 SRE 解释实际流程与风险。平台研发和数据相关人员建立事件关联、口径和看板。

指标需要对应团队可采取的行动，避免把跨角色的交付结果简单归因到某一个人。

## 3. DORA：先认识当前五项口径

截至 2026-10-16 核对的 [DORA 官方指南](https://dora.dev/guides/dora-metrics/)采用五项交付绩效指标。旧材料常讲四项，阅读时注意定义变化。

| 指标 | 简要含义 |
|---|---|
| Change lead time，变更前置时间 | 从代码提交到生产部署所需时间 |
| Deployment frequency，部署频率 | 一段时间内的部署次数或部署间隔 |
| Failed deployment recovery time，失败部署恢复时间 | 需要立即干预的失败部署恢复所需时间 |
| Change fail rate，变更失败率 | 需要立即干预的部署所占比例 |
| Deployment rework rate，部署返工率 | 因生产事件引发的非计划部署所占比例 |

失败部署恢复时间聚焦部署引发的问题，与把所有故障都混在一起计算的 MTTR 不等同。这组指标适合结合服务上下文观察趋势，不宜作为个人排名或不同业务的简单横向排名。

## 4. 怎样真正落地数据口径

下面是本文建议的平台事件设计：

| 问题 | 需要做出的约定 |
|---|---|
| 从何时算提交？ | 固定 commit 时间来源，处理合并、cherry-pick 和重复关联 |
| 什么算生产部署？ | 按应用、环境、发布记录定义，避免把每个 Pod 更新算一次 |
| 灰度算何时完成？ | 区分首次进入生产、全量、终止，保留各时间点 |
| 什么算变更失败？ | 明确用户影响和紧急干预标准，关联发布与事件 |
| 何时算恢复？ | 用服务恢复证据确认，区分工单关闭和用户恢复 |
| 哪些是返工部署？ | 记录是否非计划、由哪个生产事件触发 |
| 如何处理未知？ | 缺少关联时标记待确认，避免自动当作成功 |

不同组织可以有不同操作口径，但必须公开、稳定、可回算。调整规则时保留版本，避免趋势变化只是计算方式改变。

## 5. 用过程指标找到具体瓶颈

DORA 指标展示交付结果，过程指标帮助寻找可改进的环节。可以从以下维度入手：

| 维度 | 示例 | 可能的行动 |
|---|---|---|
| 开发协作 | 评审等待时间、变更批量 | 缩小 MR、改善评审轮值 |
| CI | 排队、拉依赖、执行、反馈耗时 | 调整资源、缓存或并行 |
| 测试 | 不稳定测试率、环境等待 | 修复脆弱测试、环境隔离 |
| CD／发布 | 审批等待、执行耗时、人工步骤 | 优化策略、自动化重复操作 |
| 运行质量 | 发布相关故障、错误预算消耗 | 补充验证、改进渐进发布 |
| 开发体验 | 首次接入耗时、自助完成率、失败原因 | 改模板、文档、报错和默认值 |
| 平台成本 | 单次构建成本、环境闲置、存储占用 | 回收资源、调整保留策略 |

采用率需要与体验和结果一起看。强制大家接入一个复杂平台，也可能让接入率很高而交付变慢。

## 6. 一个改进例子

教学场景：某服务提交到上线耗时很长。

```text
先确认时间口径
  → 拆分评审、CI 排队、执行、环境等待、审批和发布
  → 找出主要等待来自 CI 资源排队
  → 调整队列或资源分配
  → 比较调整前后等待分布与成本
```

如果主要时间花在等审批，缩短编译几秒不会解决核心问题。改进后还要检查质量、成本和其他租户是否恶化。

不要只看平均值。查看中位数与高分位、样本量和异常分布，并排除业务规模或工作负载变化造成的干扰。

## 7. 复盘要留下什么

本文建议用以下结构：

1. 影响：用户、范围、持续时间和可验证的损失。
2. 时间线：告警、发现、决策、操作和恢复。
3. 证据：日志、指标、变更与关键判断。
4. 促成因素：代码、设计、测试、环境、流程和监控的共同作用。
5. 改进项：负责人、期限、验收方法和优先级。

把“加强意识”改成可以验证的动作。例如“新增数据库慢查询对照，并在预发验证指定数据规模”，比“以后发布仔细一点”更能落地。

## 8. 技术栈与代表性开源项目

| 项目 | 用途 |
|---|---|
| [Apache DevLake](https://github.com/apache/devlake) | 研发工具数据集成与工程度量 |
| [Grafana OSS](https://grafana.com/oss/) | 指标可视化与趋势看板 |
| [OpenProject](https://www.openproject.org/) | 复盘行动项与改进任务管理 |

DevLake 等工具的内置口径与当前 DORA 定义可能存在版本差异，使用前逐项核对。平台建设可以先覆盖少量可信事件，再逐步扩大，不必先做一个完整数据仓库。

## 9. 核心技能与平台任务

| 深度 | 本章应掌握 |
|---|---|
| 理解 | 结果指标与过程指标的关系，指标无法单独解释原因 |
| 使用 | 读取趋势、拆解等待、结合访谈与事件找瓶颈 |
| 开发平台 | 事件采集、服务身份映射、数据清洗、口径版本和可回算 |

本案例要能够关联需求、提交、构建、部署和一次故障演练，按同一时间线解释交付过程。

自测：部署频率提高了一倍，但紧急修复变多、开发者更焦虑，能否直接宣称研发效能提升？
