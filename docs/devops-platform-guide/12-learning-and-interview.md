# 12｜转岗学习路线与面试准备

[返回阅读入口](README.md) · [下一章：案例与实操](13-case-study-and-lab.md)

## 1. 先保持已有优势

对有 3 年服务端经验的读者，先用熟悉的语言完成交付闭环。目标岗位如果主要使用 Go，可以再补 Go；无需为了“做 DevOps”同时重学全部技术。

下面的安排是学习建议。实际用时取决于已有基础与投入，不表示完成后就能覆盖所有公司面试。

## 2. 能力分层

| 优先级 | 能力 | 需要到什么程度 |
|---|---|---|
| P0：先补齐 | Git、Linux、HTTP／网络、自己语言的构建测试 | 能独立定位本地、CI 和运行环境差异 |
| P0：先补齐 | 容器、镜像、仓库、摘要 | 能构建、上传、固定版本并运行 |
| P0：先补齐 | 一种 CI 引擎 | 能写流水线、读报告、定位失败 |
| P0：先补齐 | 部署、配置、探针、发布和回退 | 能完成一次部署与故障演练 |
| P0：先补齐 | 指标、日志、基本运行排查 | 能解释一次业务异常及恢复证据 |
| P1：岗位重点 | 幂等、异步、状态机、对账和权限 | 能把已有服务端经验用于交付平台 |
| P1：岗位重点 | Kubernetes、GitOps、渐进发布 | 按 JD 重点，至少独立实践一条路径 |
| P1：岗位重点 | 测试分层、安全证据、平台体验 | 能理解门禁、接入成本和使用反馈 |
| P2：后续深入 | 多集群、复杂调度、供应链证明、成本治理 | 与负责模块和业务规模结合 |

已有能力不是默认全部达标。例如过去只写业务接口，也需要检查事务、消息重复、并发控制和故障恢复的实践深度。

## 3. 六个学习单元

可以按每周一个单元安排；每个单元有可复查的成果，遇到不熟悉的基础可以延长。

| 单元 | 学习与动手 | 应交出的证据 |
|---|---|---|
| 1：看懂主链 | 阅读 01、11，整理旧项目真实交付流程；实现案例接口和测试 | 一张自己的流程图、测试结果、知识缺口 |
| 2：CI 与制品 | 接入一个 CI 引擎；构建、测试、生成并登记镜像 | 成功与失败运行、完整摘要、来源关联 |
| 3：环境与部署 | 用容器和 Kubernetes／既有部署底座运行服务 | 部署定义、配置、探针和排障记录 |
| 4：发布与恢复 | 做分批更新，验证冒烟、暂停和旧版本恢复 | 发布记录、失败演练、恢复证据 |
| 5：运行态 | 接入指标和日志；制造延迟或依赖异常并定位 | 看板、时间线、告警与简短复盘 |
| 6：平台后端 | 设计或实现一个小模块，如发布任务 API | 模型、状态机、权限、幂等与故障处理说明 |

详细任务见第 13 章。先把主链跑通，再决定是否增加 GitOps、自动分析或更复杂的环境管理。

## 4. 八道场景题及回答要点

### 题一：从一次代码提交讲到生产运行

应覆盖触发、验证、可信制品、测试、环境配置、部署、流量、业务验证和运行反馈。每一步说清输入、成功条件和失败处理。

追问：同一个提交为什么可能产生不同制品？回答需要涉及依赖、基础镜像、构建工具和环境。

### 题二：CI 为什么有时很慢

先分解排队、环境准备、依赖下载、编译、测试和报告时间，再看资源、缓存、并行和测试范围。不能直接回答“增加机器”。

追问：缓存加速后怎样防止污染与版本差异？

### 题三：Webhook 重复，为什么没有重复构建

解释验签、事件 ID、业务去重键、数据库唯一约束、队列重复及执行幂等。还要允许用户显式重新运行，而不被去重逻辑永久阻止。

追问：同一 MR 的 push 与 MR 事件要合并处理吗？依据是什么？

### 题四：测试通过了，生产却失败了

考虑制品与配置不同、真实数据量、路由与权限、依赖差异、资源、并发、数据库兼容，以及测试覆盖不足。先看事实再形成假设。

追问：怎样证明测试与生产使用同一内容？要说出完整摘要和配置证据。

### 题五：发布接口超时了，该怎么办

先区分用户请求超时、平台任务超时和外部执行超时。查询已有任务与外部状态，利用幂等键和预先保存的关联标识对账。创建响应丢失时不能只依赖尚未取得的外部 ID；无法可靠定位时保留未知并人工核对，不能简单创建另一次发布。

追问：原 Worker 还在运行，新 Worker 接手后怎样防止双方同时推进？

### 题六：Pod Ready，能否判定发布成功

还要检查目标版本、实例分布、入口路由、业务冒烟、依赖和生产指标。说明探针验证的范围，以及没有流量或指标缺失时怎样处理。

追问：把数据库是否可用放进 Liveness，可能有什么副作用？

### 题七：为什么不能一键回滚所有变更

镜像、配置、数据库、消息和用户数据的恢复方式不同；新旧代码还需要兼容。解释暂停、流量切回、关闭功能、应用回退和前向修复。

追问：启用 GitOps 自动同步时，手工改集群会怎样？

### 题八：平台效能怎样评估

用交付结果、稳定性、过程等待、开发体验和成本共同判断。讲清当前 DORA 定义，再根据瓶颈选择行动，不把提交数当个人产出排名。

追问：改进前后样本、服务范围和口径怎样保持可比？

## 5. 怎样讲已有项目

选择自己真实做过的项目，用以下顺序：

```text
背景与约束
  → 自己负责什么
  → 为什么采用该设计
  → 怎样验证与发布
  → 出过什么问题，怎样判断和处理
  → 结果与局限
```

如果以前没有开发过发布平台，可以诚实说明：“业务开发里使用过相关流程，最近完成了交付闭环练习，并针对幂等、状态对账和回退做了设计。”再用实际练习证据展开。

不要把练习描述成公司生产经验，也不要编造降本、提效或大规模并发数据。

## 6. 一段练习项目介绍模板

完成相应内容后，可以据实填写：

> 我用熟悉的语言实现了一个订单查询练习服务，接入了一条包含构建、测试和镜像生成的流水线，使用固定摘要部署到练习环境。随后加入了业务冒烟、基础指标与一次失败演练。平台设计部分，我重点处理发布请求幂等、同环境互斥和外部执行超时后的状态对账。还没有实践的部分是……。

面试中比这段文字更重要的是展示流水线、报告、部署配置和故障时间线，并解释每个选择。

## 7. 拿到 JD 后重点确认

- 平台主要服务哪些团队，当前最需要解决什么问题？
- 这个岗位负责哪几个模块，日常代码开发、集成和运维分别占什么范围？
- 是基于现有工具扩展，还是自研控制面与执行引擎？
- 技术栈是 Java／Go／Python 中的哪一种，Kubernetes 要求多深？
- 谁负责基础设施和生产值班，平台自身的可用性目标是什么？
- 平台接入和使用效果怎样衡量，有没有真实开发者反馈？
- 入职前三个月预期交付什么？

这些回答能帮助判断机会是否匹配“平台后端研发”，也能决定接下来把时间投在哪个模块。

## 8. 完成学习后的自测

给自己做一次 20 分钟演示：

1. 用 3 分钟讲完整流程。
2. 用 5 分钟展示一次成功 CI 与一次失败阻断。
3. 用 5 分钟说明指定制品怎样部署、验证和恢复。
4. 用 5 分钟解释一个平台后端模块及异常路径。
5. 用 2 分钟说明没有覆盖的风险和下一步。

如果只能讲工具名字，回到相关章节补概念；如果正常路径能跑通但失败后无从下手，优先补失败、幂等和对账。

工具的官方学习入口见[第 14 章](14-glossary-and-resources.md)。
