# 03｜开发与代码协作

[返回阅读入口](README.md) · [下一章：CI](04-continuous-integration.md)

## 1. 输入、产出与重点

输入是设计与验收标准，产出是可评审的代码、自动化测试和可复现的开发说明。

对业务开发，重点是正确实现、小批次提交和有效评审。对平台开发，重点是把仓库、身份、代码事件和后续任务可靠地连接起来。

## 2. 谁负责

业务开发提交实现与测试，评审人检查正确性、兼容性、可维护性及风险。测试参与场景补充。平台团队维护仓库接入、保护规则、模板和事件处理能力。

代码平台的管理员不天然拥有每个应用的业务评审权限，平台管理员与生产发布权限也应分别表达。

## 3. 分支和评审要解决什么

本文建议练习采用“短分支＋PR／MR＋主干保护”的简单模型：

```text
main
  → feature/order-query
  → 提交代码与测试
  → PR/MR 自动检查与人工评审
  → 合并
  → 对合并后的确定提交生成交付候选
```

PR 和 MR 都是提议合并代码的协作对象，名称取决于产品。团队也可能采用其他分支策略；面试时应解释为什么选择某个流程，以及长分支、合并冲突、紧急修复怎样处理。

评审通过和自动检查通过是两类证据。平台应把“检查针对哪个提交”绑定清楚：评审后又推送新提交，旧结果是否仍有效，需要由规则决定。

[GitLab 官方资料](https://docs.gitlab.com/ci/pipelines/merge_request_pipelines/)区分普通 MR 流水线和验证合并结果的流水线。不能看到“MR 检查通过”就假设目标分支合并后的组合已被测试；还要确认执行对象以及版本功能。

## 4. 本地环境要能复现

团队至少应约定：

- 语言运行时、构建工具与依赖版本的管理方式。
- 一条明确的构建、测试和启动命令。
- 本地数据库、缓存等依赖的准备方式。
- 示例配置与密钥注入入口。
- 初始化测试数据的方法。

容器可以统一部分环境，但硬件架构、操作系统、外部依赖和运行权限仍可能不同。复现问题时要记录差异。

本案例在本地完成参数、权限、空数据和数据库查询测试；集成测试可以通过 [Testcontainers](https://testcontainers.com/) 启动临时依赖，再把同一测试入口交给 CI。

## 5. 平台收到代码事件后要做什么

下面是教学设计：

1. 校验事件来源和签名，解析仓库、提交、分支、事件类型和事件 ID。
2. 以外部事件 ID 去重，保存接收记录。
3. 判断是否需要创建流水线；同一次变更可能同时产生 push 和 MR 事件。
4. 创建内部任务并投递队列，尽快返回事件接收结果。
5. 异步执行后，将检查结果回写对应的提交和 MR。
6. 回写失败时保留重试和对账记录。

“代码事件至少送达一次”是一个有用的设计假设：平台要能接受重复、迟到和漏回调，不能靠“Webhook 应该只来一次”保证正确性。

如果外部系统没有稳定事件 ID，可以用仓库、事件类型、提交、目标分支等组成业务去重键，并说明哪些重新执行应被允许。

## 6. 技术栈与开源项目

| 能力 | 技术 | 代表性项目 |
|---|---|---|
| 版本管理 | Git、commit、分支、merge、tag | Git；代码托管可选 Gitea／GitLab 开源部分 |
| 评审与规则 | PR／MR、保护分支、检查状态 | [Gitea](https://docs.gitea.com/)、[GitLab](https://gitlab.com/gitlab-org/gitlab-foss) |
| 事件集成 | HTTP、Webhook、鉴权、队列、数据库 | 基于代码平台 API 开发适配器 |
| 开发依赖 | 容器、测试夹具、依赖生命周期 | [Testcontainers](https://testcontainers.com/) |

## 7. 核心技能

| 深度 | 应达到的能力 |
|---|---|
| 理解 | 知道 commit、分支、tag 和 PR／MR 的区别，知道评审与验证绑定的对象 |
| 使用 | 处理冲突、阅读 diff、补充测试、检查提交状态和事件记录 |
| 开发平台 | 实现事件验签、幂等、权限校验、异步触发、检查回写和补偿 |

已有服务端经验的迁移点非常直接：Webhook 就是一个有认证与幂等要求的接入 API；流水线触发是异步业务流程；检查回写是外部系统集成。

## 8. 本阶段的交付证据

本案例进入后续阶段时，至少能定位需求、MR、具体 commit、评审结果和自动检查结果。出现“本地通过，CI 失败”时，应能比较依赖、运行时、环境变量和测试数据。

自测：同一个 MR 的旧提交测试通过，新提交还没测，平台应该显示什么？为什么不能只在 MR 表里保存一个 `success=true`？
