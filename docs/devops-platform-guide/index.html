CHAPTER 00

服务端开发转 DevOps／研发效能平台：从需求到生产运行

先建立坐标

面向有约 3 年服务端开发经验、准备应聘研发效能平台后端研发岗位的读者。

推荐使用单页 HTML 完整版阅读：包含完整正文、流程图、目录、全文搜索和阅读进度，单独保存这一份 HTML 即可离线打开。

这套指南用一个功能的交付过程回答三个问题：功能经过哪些阶段；每个阶段做什么、谁负责、依赖什么技术；平台工程师需要把哪些事情做成可复用的能力。

资料核对日期：2026-10-16。岗位分工是本文的教学模型，工具定位以各章官方参考资料为依据。实际公司的流程、权限和产品版本可能不同；阅读 JD 和面试交流时需要对应确认。

先抓住岗位的工作对象#

过去写业务服务，主要面对订单、账户、支付等业务对象。开发研发效能平台，主要面对应用、代码仓库、构建任务、制品、环境、发布单和运行事件。

你已有的接口设计、数据库、异步任务、权限、并发控制和故障排查经验都能迁移。需要补齐的是软件交付过程，以及这些对象之间的状态、约束和失败处理。

本文会分别讨论：

  • 业务开发怎样借助平台交付功能。
  • 平台后端怎样实现流水线、发布编排、环境管理和运行反馈。
  • 平台依赖的 Jenkins、Kubernetes 等系统各自负责什么。

4. 四个容易混淆的边界#

CI 是持续集成。 核心是频繁集成变更，并用自动化验证尽快暴露问题。有一个构建按钮不等于团队已经形成良好的持续集成实践。

CD 可能指两件事。 持续交付强调变更保持可发布，进入生产可保留人工决策；持续部署进一步让满足规则的变更自动进入生产。具体公司说“CD”时，需要确认指哪一种。本文的交付流程采用可保留人工生产决策的模型，工具实现参见 Jenkins Pipeline 和 GitLab CI/CD。

部署、发布、功能开放是三个可分别控制的动作。 部署把软件放进环境并运行；发布让目标用户或流量使用新版本；功能开放还可能受功能开关控制。公司内部可能把它们都叫“上线”，平台研发需要把实际动作和成功条件拆清楚。生产策略的实现边界见 Argo Rollouts 流量管理。

运行态持续存在。 流水线结束后，还要知道用户能否成功访问、延迟是否异常、服务容量是否足够。相关方法见 Google SRE：服务目标。

5. 贯穿各阶段的“证据链”#

平台需要能回答：线上这个版本从哪里来、为什么能发布、谁发布的、上线后怎样。

text
需求 REQ-123
  → MR-42 / Git commit
  → PipelineRun / 测试报告
  → Artifact digest / 扫描结果
  → Deployment / 环境配置版本
  → Release / 审批 / 流量变化

这是本文建议的平台领域模型，不是某款产品的统一标准。关键是使用可关联的稳定标识，避免只在页面里写一段无法追溯的文本。

6. 对转岗读者的优先级#

最先需要解释清楚的是：一次代码提交怎样变成生产中的某个版本；每一步怎样判断成功；失败时怎样恢复。

接着学习 CI、制品、CD、发布和运行态的实际操作。最后选择一个平台模块深入设计，例如“发布单状态机＋同环境互斥＋回调幂等＋超时对账”。

自测：如果测试通过了，但生产接口一直超时，可能是哪几个阶段的哪些假设没有得到验证？阅读后续章节时持续带着这个问题。

1. 阶段一：需求承接#

输入、产出与重点#

输入是业务目标，例如“用户想快速找到已经支付的订单”；产出是可验收的功能范围、优先级、依赖和交付安排。

需求中应该说明正常行为，也应该约定空结果、非法参数、权限不足和失败反馈。对平台研发而言，需求还需要关联服务、代码仓库、负责人及预期发布批次，便于后续追踪。

谁负责#

产品或业务负责人确认用户价值、范围和验收标准。业务开发评估实现与依赖，测试提前发现边界条件，技术负责人协调风险和拆分。研发效能平台团队负责需求系统与研发流程的连接能力。

共用案例的需求记录#

项目教学示例
功能GET /orders?status=paid&limit=20
身份与权限使用认证上下文，只能查当前用户自己的订单
排序与分页按创建时间倒序；明确相同时间的稳定排序及分页规则
参数status 使用明确枚举；limit 有默认值和上限
业务验收正常数据、空结果、非法参数、未认证、跨用户访问均有预期
性能目标在约定数据量和负载下验证；示例目标为 P95 小于 300ms

这里的 300ms 只用于练习。正式目标要由业务体验、已有基线、访问规模和成本共同决定。

技术栈与代表性项目#

需要理解 Issue、看板、工作流、权限、Webhook 和系统间 API。可以查看 OpenProject、Plane 开源版 和 Gitea Issues 如何表达任务、状态和协作。

2. 阶段二：技术设计#

输入、产出与重点#

输入是明确的需求；产出是团队能够实现、测试、部署和维护的方案。

设计范围包括 API 契约、数据访问、依赖行为、兼容性、运行观测和发布方案。对一个查询接口，除了 Controller 和 SQL，还要考虑超时、分页、索引、用户隔离和失败码。

谁负责#

业务开发或技术负责人主导方案。测试参与可验证性设计；安全团队按风险参与鉴权、数据和供应链评审；SRE 或基础设施团队协助容量与运行约束；平台团队提供标准模板和自动检查。

本案例需要做的设计判断#

  1. API 契约：字段、状态码、错误结构和分页语义是什么？客户端是否能识别错误？
  2. 数据访问：SQL 是否包含用户条件？扫描量是否随数据增大失控？需要新增什么索引？
  3. 兼容性：新旧代码共存时，响应和数据库结构是否都可用？
  4. 依赖与资源：数据库超时、连接池和并发上限怎样约束？请求取消后是否停止无用工作？
  5. 可观测性：请求数、失败率、延迟、慢查询和版本信息怎样关联？
  6. 发布：先部署到哪里，如何验证，小流量怎样放，什么情况下暂停？
  7. 恢复：旧版本能否读取新结构？已执行的数据变更是否需要前向修复？

设计记录可以采用简短 ADR：问题、可选方案、选择、理由、代价和回退条件。无需为小功能写冗长文档，但需要保留影响交付与运行的关键决策。

技术栈与代表性项目#

基础是 HTTP、SQL、索引、事务、认证授权、缓存及超时处理。使用 OpenAPI 描述 HTTP API 契约，使用 Mermaid 表达依赖和时序；跨服务行为验证可以进一步了解 Pact。

OpenAPI 是规范，Mermaid 是图示工具，Pact 是契约测试工具。它们分别解决表达和验证的一部分问题，设计判断仍需要开发者完成。

1. 输入、产出与重点#

输入是设计与验收标准，产出是可评审的代码、自动化测试和可复现的开发说明。

对业务开发，重点是正确实现、小批次提交和有效评审。对平台开发，重点是把仓库、身份、代码事件和后续任务可靠地连接起来。

2. 谁负责#

业务开发提交实现与测试，评审人检查正确性、兼容性、可维护性及风险。测试参与场景补充。平台团队维护仓库接入、保护规则、模板和事件处理能力。

代码平台的管理员不天然拥有每个应用的业务评审权限，平台管理员与生产发布权限也应分别表达。

3. 分支和评审要解决什么#

本文建议练习采用“短分支＋PR／MR＋主干保护”的简单模型：

text
main
  → feature/order-query
  → 提交代码与测试
  → PR/MR 自动检查与人工评审
  → 合并
  → 对合并后的确定提交生成交付候选

PR 和 MR 都是提议合并代码的协作对象，名称取决于产品。团队也可能采用其他分支策略；面试时应解释为什么选择某个流程，以及长分支、合并冲突、紧急修复怎样处理。

评审通过和自动检查通过是两类证据。平台应把“检查针对哪个提交”绑定清楚：评审后又推送新提交，旧结果是否仍有效，需要由规则决定。

GitLab 官方资料区分普通 MR 流水线和验证合并结果的流水线。不能看到“MR 检查通过”就假设目标分支合并后的组合已被测试；还要确认执行对象以及版本功能。

4. 本地环境要能复现#

团队至少应约定：

  • 语言运行时、构建工具与依赖版本的管理方式。
  • 一条明确的构建、测试和启动命令。
  • 本地数据库、缓存等依赖的准备方式。
  • 示例配置与密钥注入入口。
  • 初始化测试数据的方法。

容器可以统一部分环境，但硬件架构、操作系统、外部依赖和运行权限仍可能不同。复现问题时要记录差异。

本案例在本地完成参数、权限、空数据和数据库查询测试；集成测试可以通过 Testcontainers 启动临时依赖，再把同一测试入口交给 CI。

5. 平台收到代码事件后要做什么#

下面是教学设计：

  1. 校验事件来源和签名，解析仓库、提交、分支、事件类型和事件 ID。
  2. 以外部事件 ID 去重，保存接收记录。
  3. 判断是否需要创建流水线；同一次变更可能同时产生 push 和 MR 事件。
  4. 创建内部任务并投递队列，尽快返回事件接收结果。
  5. 异步执行后，将检查结果回写对应的提交和 MR。
  6. 回写失败时保留重试和对账记录。

“代码事件至少送达一次”是一个有用的设计假设：平台要能接受重复、迟到和漏回调，不能靠“Webhook 应该只来一次”保证正确性。

如果外部系统没有稳定事件 ID，可以用仓库、事件类型、提交、目标分支等组成业务去重键，并说明哪些重新执行应被允许。

1. 本阶段解决什么#

3. 一次 CI 的完整路径#

4. 先认识执行模型#

概念含义平台研发关注点

不同产品叫法和粒度不同。例如 Jenkins 使用 Pipeline、Stage、Step、Agent 等概念；GitLab 使用 Job、Stage 和 Runner，并支持按依赖组织执行。平台的内部模型需要做清晰映射。

5. 一个简化的流水线例子#

以下是 Java 项目中的 Jenkinsfile 教学片段：项目已提交 Maven Wrapper，Jenkins Agent 已准备兼容的 JDK，控制器已安装所需 Pipeline 与 JUnit 功能。语言不同就替换对应的构建和测试入口。

groovy
pipeline {
    agent { label 'java-build' }
    options {
        timeout(time: 15, unit: 'MINUTES')
    }
    stages {
        stage('Verify') {
            steps {
                sh './mvnw -B verify'
            }
        }
    }
    post {
        always {
            junit testResults: '**/target/surefire-reports/*.xml',
                  allowEmptyResults: false
        }
    }
}

这个片段只示意“运行验证＋收集单元测试报告”。它没有实现本章其余平台能力，也未自动收集所有集成测试报告。项目若使用 Failsafe 等工具，需要追加对应报告路径并确认 verify 确实执行了测试。

关键是失败要向上传播：不要为了让流水线变绿，在测试命令后附加忽略错误的逻辑。报告缺失也需要有明确含义，避免“根本没跑测试”被展示成测试成功。

6. 质量门禁怎样定义#

质量门禁是进入下一步的条件，可以包含：

  • 编译和必选测试成功。
  • 代码与依赖检查达到团队规则。
  • 必需的评审已完成，且对应当前提交。
  • 制品来源、扫描与签名满足发布要求。
  • 测试报告存在且可追溯。

规则应版本化，并记录阻断原因。覆盖率是辅助证据，不能单独代表质量；对支付、权限、幂等等关键行为，有意义的测试比追求统一百分比更重要。

对历史存量问题，可以区分新增风险与已有风险。允许例外时应绑定审批、理由、范围和过期时间，避免永久绕开规则。

7. 平台后端真正难在哪里#

7.1 调度与资源#

排队慢、执行慢、拉取依赖慢是不同问题。先把时间拆开，再决定是增加 Agent、优化依赖下载，还是调整任务并行。

需要理解资源配额、租户公平性、任务标签、执行超时和孤儿任务回收。对外暴露“等待资源”比一直显示“执行中”更有用。

7.2 状态与恢复#

教学状态可以是：

text
CREATED → QUEUED → RUNNING → SUCCEEDED / FAILED / CANCELED

还需记录外部任务 ID、执行尝试、心跳和最后对账时间。Runner 断连时，任务结果可能未知；先查询和对账，再决定是否重试。外部任务已完成但平台没收到回调，与任务从未执行，是两种情况。

创建外部任务前保存内部运行与尝试 ID，并尽量让外部任务携带可查询的关联标识。若创建响应丢失，仍需要有定位任务的方法；外部系统不提供可靠关联时，应保留结果未知并人工核对。

取消请求也不等于任务已停止。平台要区分“用户请求取消”和“执行器已确认停止”，并说明哪些副作用已经发生。

7.3 重试与幂等#

网络暂时不可用可以有限重试；编译错误、业务断言失败通常需要修复。对不稳定测试，应保留首次失败与重试结果并推进治理。

构建、上传、登记制品可能有副作用。每次重试都应有明确的尝试 ID，并保证重复回调不会重复创建制品或触发发布。

7.4 执行隔离与凭据#

构建任务会运行仓库中的代码，因此要明确代码信任边界。外部贡献的 MR、普通分支和受保护分支不应默认获得相同凭据。

执行环境应按风险隔离，凭据按任务和环境最小化授予。日志需要避免泄露密钥；平台不能仅靠界面隐藏来保护后端资源。

7.5 缓存与可复现#

依赖缓存可以提速，但缓存命中不代表内容可信或构建正确。缓存键要考虑依赖声明、运行时和架构等差异；不可信任务不能随意覆盖可信任务使用的缓存。

依赖版本、基础镜像、构建工具和网络来源也会影响输出。记录 commit 只是来源追踪的一部分。

1. 输入、产出与重点#

2. 谁负责#

业务开发定义打包方式与依赖。平台或仓库团队提供上传、下载、授权、保留和可用性能力。安全团队制定风险规则。发布负责人确认指定制品具备进入目标环境的证据。

3. Tag 和 Digest 为什么不同#

例如：

text
registry.example.com/team/order-service:git-a1b2c3d
registry.example.com/team/order-service@sha256:<完整摘要>

第一种使用人类可读的标签，第二种按内容摘要寻址。标签是否可覆盖取决于仓库策略；摘要用于固定具体内容。正式记录应保存完整摘要，不能只保存缩写或 latest。

OCI 的内容描述及摘要约束见 OCI Image Specification。Harbor提供标签不可变策略，实施前需要检查匹配规则。

多架构镜像还要记录目标平台，区分镜像索引摘要与平台镜像摘要。示例中的摘要表达的是引用方式，尖括号部分需替换为真实值。

4. 一份制品需要关联什么#

建议的最小元数据：

字段用途
服务、仓库与 commit关联来源和负责人

运行平台与架构避免构建与部署目标不匹配

晋级表示这份制品满足进入下一环境的条件。可以通过元数据、仓库分区或镜像复制表达，关键是明确源摘要、目标摘要和验证证据。

1. 输入、产出与重点#

输入是明确的代码或制品版本、测试范围、测试数据和环境；产出是可复查的验证证据、缺陷及剩余风险。

2. 谁负责#

业务开发对实现及基础自动化测试负责。测试人员补充系统场景、组织质量验证并推动风险闭环。产品或业务代表确认业务验收。平台团队提供环境、执行、报告和证据关联能力。

测试团队的确认不替代业务开发的质量责任；平台上的“通过”也需要能追溯到具体测试范围。

3. 各类测试分别验证什么#

类型本案例的检查内容适合位置主要局限
单元测试参数限制、状态判断、用户条件构造本地／CI常隔离了真实依赖
数据访问集成测试真实数据库的 SQL、排序、分页、索引行为CI 临时依赖／集成环境数据规模与生产可能不同
API 测试身份、状态码、响应结构、越权、空结果本地服务／部署后不一定覆盖前端用户路径
契约测试消费方与提供方对字段和交互的约定CI／跨服务验证需要参与方维护契约
端到端测试用户进入页面、筛选并查看订单测试／预发环境成本和脆弱性较高
性能与容量验证延迟、吞吐、慢 SQL、资源饱和受控压测环境必须说明数据量与负载模型
安全验证用户隔离、注入、敏感信息、依赖风险CI＋专项环境扫描器不能覆盖全部业务风险
业务验收结果是否满足需求与体验测试／预发环境不覆盖所有技术正确性
上线冒烟生产路由、权限、依赖和核心查询能否工作发布过程中场景少，不能替代完整测试

测试层次是选择验证手段的思路，不意味着每个项目都要配置相同数量的测试或独立平台。

4. 环境和数据常常比测试脚本更难#

环境可识别#

需要记录运行中的制品摘要、部署配置、依赖版本、数据库结构和测试时间。出现问题时，才能知道测试的是哪套组合。

共享环境上被另一组发布覆盖，是一种环境冲突。可以通过预约、隔离命名空间或临时环境缓解，但隔离同时还要考虑账号、数据、队列和外部服务。

数据可构造#

本案例至少准备两个不同用户、各类订单状态、空结果和分页边界。大数据量验证还要设计合理分布，不能只插几条记录就宣称性能满足生产目标。

测试数据使用合成数据或经过批准的脱敏流程。练习中用合成用户与订单即可。

依赖可控制#

Mock 便于构造失败，但与真实服务行为可能有偏差。对关键依赖应结合契约测试、真实集成和超时场景验证。

使用 Testcontainers 管理测试中的容器依赖时，还要确认执行器具备所需容器运行能力和资源；它并不自动解决所有跨服务环境问题。

1. 输入、产出与重点#

输入是已识别的制品、目标环境、部署定义、配置与授权；产出是目标环境中的实际版本及其状态证据。

2. 谁负责#

业务团队确认部署内容、配置需求和业务风险。平台团队维护环境模型、部署入口、编排和状态反馈。基础设施团队管理集群、网络、存储等底座。SRE 按组织分工参与运行标准、容量和生产稳定性。

生产操作的发起人、批准人和执行身份需要可识别。审批应绑定具体变更内容，制品或配置变化后应重新判断审批是否有效。

3. 先分清四种对象#

对象表达什么本案例
制品要运行的内容order-service 的镜像摘要

5. 两种常见部署路径#

路径 A：平台驱动执行#

text

  → 执行器调用部署工具或 Kubernetes API

text

7. 怎样判断部署完成#

至少区分四层证据：

  1. 请求被接受：API 已接收清单或任务。
  2. 资源达到目标：控制器观察到目标配置，副本逐步更新。
  3. 实例可以接收流量：探针、服务端点和依赖满足就绪条件。
  4. 业务验证通过：从实际入口执行必要冒烟，结果符合预期。

前三层属于部署控制与资源健康证据，第四层开始连接业务验证。平台应明确展示当前到哪一层，不能把执行命令返回 0 直接解释成用户可用。

具体字段和更新条件依 Kubernetes 资源类型而异，见 Deployment 官方资料。观察一个 Deployment 时，需要确认状态对应本次目标版本，避免误读旧状态。

并发与对账#

同一应用、同一环境的变更可能冲突。平台可以排队、拒绝或显式替代，关键是规则可解释。锁失效后还要防止旧执行者继续写入，可结合操作版本或 fencing token。

如果外部系统无法可靠定位这次操作，应保留“结果未知”并转受控人工核对，避免盲目重试。具备足够证据时，平台重启后通过对账恢复推进，防止重复执行迁移或覆盖新的发布。

1. 输入、产出与重点#

输入是明确的候选制品、配置、验证证据、发布策略和授权；产出是经过生产观察的版本，以及完整的发布过程记录。

部署完成意味着软件已按定义运行；生产发布还需要决定哪些用户使用新版本、怎样观察、什么时候扩大、何时停止。功能开关又可以独立决定功能是否对用户开放。

2. 谁负责#

发布负责人确认本次变更范围、操作节奏与异常决策。业务开发保证实现与兼容，测试提供验证证据，SRE 协助运行风险和故障处置，平台团队提供发布编排与控制能力。

这些职责可以由不同岗位或同一人承担。发布前需要明确：谁有权暂停、回退和恢复，异常找谁，多久升级。

3. 常见发布策略#

策略实际动作适合认识的优点要承担的约束
滚动更新逐批替换实例复用现有部署机制新旧版本共存，需要兼容和容量余量
蓝绿同时准备两组版本，再切换入口流量切换边界清晰额外资源、连接与数据兼容
金丝雀／灰度先给新版本部分流量或用户，再逐步扩大在较小范围观察风险需要分组、路由、观察和停止规则
功能开关控制已部署代码中的功能入口可以分别控制部署和功能开放需要管理权限、默认值、失效及过期清理

这些机制可以组合。功能开关关闭后，已经写入的数据、发出的消息和执行过的迁移仍然存在，需要另外处理。

Kubernetes Deployment 支持滚动更新；更细的灰度策略可参考 Argo Rollouts。按请求分配权重需要相应流量管理能力，不能简单把“1 个新 Pod、9 个旧 Pod”等同于精确的 10% 请求，见 流量管理说明。

4. 一次生产发布应该经过哪些判断#

发布前#

  • 固定制品摘要、部署定义、配置、目标环境和策略版本。
  • 核对测试、风险例外、审批和依赖状态。
  • 确认数据库变更顺序和旧版本兼容范围。
  • 准备新旧版本观测、冒烟和恢复操作。
  • 确认资源、值班和变更冲突。

审批应该对应具体输入。审批后替换镜像或关键配置，需要重新判断原审批是否仍适用。

发布中#

  1. 建立新版本实例，确认启动和就绪。
  2. 从实际业务入口执行冒烟。
  3. 按策略引入目标流量。
  4. 观察新旧版本及共享依赖，判断继续、暂停或停止。
  5. 扩大范围，直到完成约定的发布阶段。

发布后#

确认版本分布与配置，保留观察窗口、发布记录及异常关联。流水线退出后仍要持续监控，不能只看发布那几分钟。

5. 本案例的教学灰度规则#

以下为练习方案，数值用于帮助理解，不是通用生产标准：

项目教学约定
阶段测试 → 预发 → 小流量 → 扩大 → 全量
冒烟合法用户可查、空结果正确、跨用户被阻止
新版观测对 /orders 按版本观察失败率、P95、流量和数据库耗时
绝对目标示例：有效请求成功率至少 99.9%，P95 小于 300ms
相对比较与同一窗口的旧版本对照，并解释请求构成差异
样本要求示例：每阶段至少观察 5 分钟，且新版本有至少 1000 个有效请求
证据不足未达到样本量或关键指标缺失时，继续等待或人工判断
异常动作停止扩大，评估切回旧版本、关闭功能或其他止损方式

这些条件需要结合使用。刚好 1000 次请求时，极少的失败就会显著影响比例；少量样本也难以稳定估计尾延迟。演练阈值不能直接复制成生产规则。

自动分析至少区分“通过、失败、结果不确定”。监控查询错误、没有流量和没有错误请求是不同情况。Argo Rollouts Analysis提供指标分析及相应控制机制，具体模板需要按实际指标设置。

6. 数据库变更为什么是发布难点#

应用可以切回旧镜像，数据库和用户数据未必能恢复原样。

对新增字段或格式调整，可研究“先扩展、再迁移、最后收缩”的兼容策略：

text
增加兼容结构
  → 部署兼容新旧结构的代码
  → 分批迁移或补齐数据
  → 验证新读写路径
  → 经过兼容窗口后再删除旧结构

新增索引也要评估数据库版本、锁、磁盘和运行影响；“只加索引”不能自动视作无风险操作。本案例可以把索引变更作为独立任务，记录执行结果，再部署查询代码。

迁移任务应有唯一版本、执行记录和并发保护。执行超时后先检查真实状态，不能直接重复做非幂等变更。

7. 回滚、终止和修复要分别表达#

操作目的需要确认
暂停暂停后续推进，便于判断当前流量、实例和观察是否仍受控
终止灰度停止本轮新版本扩散实际流量是否切回、后台控制器是否继续动作
应用回退运行旧制品或旧配置与当前数据库、消息和依赖是否兼容
关闭功能停用特定用户入口是否真的覆盖所有入口及副作用
前向修复发布修正版解决问题修复风险、验证与完成时间

回退是一项需要验证结果的操作。平台至少记录目标版本、路由和实例状态，再执行必要业务检查。

GitOps 模式还要处理 Git 中的期望状态。Argo CD 自动同步文档说明启用自动同步时的回退限制，不能把历史回退按钮当作所有场景下都可直接执行的方案。

8. 平台后端的典型开发任务#

发布平台可以采用以下教学状态：

text
DRAFT → VALIDATING → APPROVAL_PENDING → READY
  → DEPLOYING → VERIFYING → CANARY → OBSERVING → SUCCEEDED

异常与控制分支包括 PAUSED、ABORTING、ROLLING_BACK、ROLLED_BACK 和 FAILED。每个状态要写清进入条件、允许动作、超时和外部系统状态。

关键实现包括：

  • 审批绑定输入快照，变更后重新校验。
  • 同环境发布互斥，防止两个任务交叉推进。
  • 指标查询与判断规则版本化，记录窗口、样本和结果。
  • 重复或迟到的回调不能覆盖更新状态。
  • 平台重启后，基于执行步骤和外部状态恢复。
  • 终止或回退期间，停止旧的自动推进任务。
  • 所有操作保存身份、原因、输入、结果和关联 ID。

1. 输入、产出与重点#

输入是持续运行的服务、运行配置、流量、依赖和服务目标；产出是对服务状态的判断、可执行的告警、事件处置记录和改进项。

需要回答：用户是否正常使用服务，异常在哪里，怎样先恢复，怎样减少再次发生。可观测数据是判断依据；看板和工具本身不替代判断。

2. 谁负责#

服务所属团队对服务行为与业务结果负责。SRE 按组织分工提供可靠性工程、值班和生产保障能力。平台团队提供采集接入、发布关联、告警路由和诊断入口。基础设施团队对底层平台负责。

平台后端岗位是否承担业务值班、平台自身值班，或者二者都承担，需要在面试中确认。

3. 从用户视角到系统内部#

视角本案例要观察什么典型用途
用户／业务是否能查到正确订单、权限是否正确判断用户影响
服务接口流量、失败率、延迟、并发快速识别服务变化
应用进程线程／协程、堆、GC、连接池、事件循环定位应用资源问题
依赖SQL、连接数、锁、缓存、下游调用定位外部等待和瓶颈
容器与主机CPU、内存、磁盘、网络、重启与调度定位资源与运行环境问题
变更镜像、配置、扩缩容、数据库、路由形成排查假设

不要看到 CPU 正常就认定服务正常。数据库等待、线程池排队、网络故障和权限错误都可能影响用户。

4. 三类常用可观测数据#

数据擅长回答要注意
Metrics 指标何时发生、多大范围、趋势怎样标签基数、采样间隔、聚合与统计窗口
Logs 日志某次行为发生了什么、错误上下文是什么结构化、脱敏、关联 ID、成本
Traces 链路一次请求经过哪些服务、耗时分布在哪里传播上下文、采样、异步和缺失节点

实际系统还可能使用剖析等数据。本指南先掌握上述三类。

OpenTelemetry提供插桩、生成、采集与导出等能力，通常还需要后端存储、查询和展示系统。使用 OpenTelemetry 不等于已经获得完整的监控平台。

5. 指标、SLO 和错误预算#

本文采用如下教学约定：

  • SLI：衡量用户体验的实际指标，例如有效查询请求的成功比例。
  • SLO：为 SLI 设定目标，例如滚动 30 天内成功比例至少 99.9%。
  • SLA：对外的服务承诺及相应约定，需要结合合同和业务定义。
  • 错误预算：在所定目标内允许的不良事件份额。

对请求成功率 SLO，若窗口内有 100 万个有效请求、目标为 99.9%，允许的不良请求份额为 1000 次。它不是固定的一段停机分钟数。需要结合是否均匀有流量来解释影响。

服务目标相关方法参见 Google SRE：Service Level Objectives。本文例子是为案例自拟的口径。

必须定义分母和失败#

本案例可以把正常合法查询作为有效请求，把服务端错误、超时或违反约定的异常响应视作不良事件；无权限或非法参数是否进入分母，需要按业务目标明确。

如果只统计应用收到的请求，入口连接失败可能完全看不到。应结合入口指标、合成探测或用户侧证据，说明测量的覆盖范围。

6. 探针通过为什么仍然可能有问题#

Kubernetes 中需要区分：

探针判断目标设计注意
Startup应用是否完成启动为慢启动提供合理空间
Readiness实例是否适合接收流量要与实际接流量能力匹配
Liveness实例是否需要通过重启恢复避免因共享依赖异常造成重启风暴

具体失败行为见 Kubernetes Probes。探针可以验证必要条件，但通常不执行完整业务路径。

例如 GET /readyz 只检查进程与连接池状态，而 /orders 缺少索引导致慢查询。此时 Pod 可能 Ready，业务延迟依然很高。

7. 指标和日志怎样接入#

建议先做一套能解释案例的最小数据：

  • 接口请求数，按路由模板、状态类别等有限维度区分。
  • 请求耗时直方图，支持观察尾延迟。
  • 数据库操作耗时、连接池使用和等待。
  • 结构化请求日志：时间、路由、状态、耗时、trace ID、版本。
  • 版本与发布标记，便于把异常与变更关联。

订单 ID、用户 ID、完整 URL 通常不适合成为指标标签，会产生大量时间序列。细粒度标识应按需要放在受控日志或链路中，并考虑隐私与成本。相关建议见 Prometheus Instrumentation。

观测新旧版本时也要控制版本标签的生命周期，避免永久保留无限增长的版本组合。

一个延迟查询示意#

假设服务已经暴露经典直方图 order_request_duration_seconds_bucket，含 route 和 le 标签：

plaintext
histogram_quantile(
  0.95,
  sum by (le) (
    rate(order_request_duration_seconds_bucket{route="/orders"}[5m])
  )
)

它表达过去 5 分钟数据的 P95 估计。桶边界、请求样本和采集完整性会影响判断；没有数据不代表延迟是 0。分组查看版本时，应在聚合中保留对应标签。

公式与直方图行为参见 Prometheus Histograms。这段示例依赖应用先提供约定指标，不能直接套用任意语言默认指标名。

8. 告警怎样做到可行动#

一条告警至少包含：

text
发生什么、影响哪个服务和环境、从何时开始
  + 严重程度、责任人与路由
  + 指标与相关发布链接
  + 当前证据、建议检查步骤与升级路径

需要区分“指标超过阈值”和“应该叫醒人”。业务不可用、持续失败、预算快速消耗等问题更接近行动触发；短暂抖动或单机异常可能适合聚合、延迟判断或工单。

Alertmanager提供告警分组、路由、抑制和静默等能力。平台还需要维护负责人、服务关系和运行手册。

发布期可以调整关联与展示，但不能为了让发布页面干净而无条件屏蔽生产故障。

9. 一次故障处理的思路#

以下是本文建议的通用排查顺序：

  1. 确认影响：哪个入口、用户范围、失败或变慢程度，是否仍在扩大。
  2. 建立时间线：何时开始，是否伴随代码、配置、数据库、流量或基础设施变更。
  3. 先做可验证的止损：暂停发布、切流、关闭功能、扩容等，需要结合原因和副作用选择。
  4. 逐层缩小范围：入口 → 服务 → 依赖 → 资源，使用指标、日志和链路互相验证。
  5. 确认恢复：从用户路径检查，比较故障前后指标，观察是否反复。
  6. 记录与改进：保留事实、证据、决策和责任明确的后续任务。

“刚发布过”只能形成相关性假设。要看异常是否集中在新版本、是否有相应调用与资源证据，以及止损后结果是否符合预期。

本案例：Ready，但订单查询很慢#

可能的证据链：

text
新版 /orders P95 升高
  → Trace 的数据库 span 占主要耗时
  → 数据库指标显示查询扫描量／等待异常
  → 核对 SQL、索引和执行计划
  → 暂停放量并验证止损

也可能是连接池过小、依赖超时、资源不足或请求构成变化。应保留备选假设，而不是看到一条慢日志就直接下结论。

1. 输入、产出与重点#

输入是需求、代码、测试、构建、部署和运行事件，以及开发者反馈；产出是明确的瓶颈、改进任务和效果验证。

平台的价值需要同时看交付速度、质量、使用体验和运行成本。流水线数量增加、页面访问量提高，只能说明活动或采用情况，不能单独证明交付变好。

2. 谁负责#

业务与平台负责人共同确定改进目标。开发、测试和 SRE 解释实际流程与风险。平台研发和数据相关人员建立事件关联、口径和看板。

指标需要对应团队可采取的行动，避免把跨角色的交付结果简单归因到某一个人。

3. DORA：先认识当前五项口径#

截至 2026-10-16 核对的 DORA 官方指南采用五项交付绩效指标。旧材料常讲四项，阅读时注意定义变化。

指标简要含义
Change lead time，变更前置时间从代码提交到生产部署所需时间
Deployment frequency，部署频率一段时间内的部署次数或部署间隔
Failed deployment recovery time，失败部署恢复时间需要立即干预的失败部署恢复所需时间
Change fail rate，变更失败率需要立即干预的部署所占比例
Deployment rework rate，部署返工率因生产事件引发的非计划部署所占比例

失败部署恢复时间聚焦部署引发的问题，与把所有故障都混在一起计算的 MTTR 不等同。这组指标适合结合服务上下文观察趋势，不宜作为个人排名或不同业务的简单横向排名。

4. 怎样真正落地数据口径#

下面是本文建议的平台事件设计：

问题需要做出的约定
从何时算提交？固定 commit 时间来源，处理合并、cherry-pick 和重复关联
什么算生产部署？按应用、环境、发布记录定义，避免把每个 Pod 更新算一次
灰度算何时完成？区分首次进入生产、全量、终止，保留各时间点
什么算变更失败？明确用户影响和紧急干预标准，关联发布与事件
何时算恢复？用服务恢复证据确认，区分工单关闭和用户恢复
哪些是返工部署？记录是否非计划、由哪个生产事件触发
如何处理未知？缺少关联时标记待确认，避免自动当作成功

不同组织可以有不同操作口径，但必须公开、稳定、可回算。调整规则时保留版本，避免趋势变化只是计算方式改变。

7. 复盘要留下什么#

本文建议用以下结构：

  1. 影响：用户、范围、持续时间和可验证的损失。
  2. 时间线：告警、发现、决策、操作和恢复。
  3. 证据：日志、指标、变更与关键判断。
  4. 促成因素：代码、设计、测试、环境、流程和监控的共同作用。
  5. 改进项：负责人、期限、验收方法和优先级。

把“加强意识”改成可以验证的动作。例如“新增数据库慢查询对照，并在预发验证指定数据规模”，比“以后发布仔细一点”更能落地。

5. 设计一个发布 API#

教学接口：

  "environmentId": "staging",

  "strategyRevision": "rolling-v2"
}

一个可靠的接收流程：

  1. 验证身份、租户、应用和环境权限。
  2. 规范化业务参数并计算请求指纹，在确定的权限范围内查询幂等键。
  3. 同一键、同一请求返回已有记录；同一键、不同内容返回冲突。
  4. 仅对新请求固定制品、配置与策略输入，检查证据与当前门禁。
  5. 原子创建发布记录与待发事件，并处理幂等键竞争和同环境并发。
  6. 返回发布 ID 和查询入口；异步推进并记录步骤。

可以返回 202 Accepted 表达任务已接受，但它不能表示发布成功。客户端通过查询接口或事件订阅获取后续结果。

注意：幂等键的作用域、有效期和请求指纹要明确。调用者没有权限时，即使猜中已有幂等键，也不能读取别人的发布结果。

查重应先于可变门禁检查。某个发布已被接受，客户端因超时重复请求，此时审批或扫描证据可能已经过期；重复请求应返回既有记录，而非重新创建或丢失原结果。任务开始执行或正式放量前是否再次检查门禁，由执行规则另行决定并记录。

6. 六个高频工程难点#

6.1 外部成功，平台未知#

网络超时后，Kubernetes 或 Jenkins 可能已执行操作。已获得外部 ID 时保存它并查询真实状态，必要时进入待对账状态。

最难的情况是外部已经创建成功，但包含 ID 的响应丢失。调用前应持久化内部操作 ID，并尽可能通过确定性资源名、标签、外部幂等令牌或可查询关联字段定位结果。选择方法时要验证外部系统实际支持的查询与一致性语义。

如果外部系统既不支持幂等创建，也无法可靠查询对应结果，应保留“结果未知”，提供人工核对与受控恢复路径。对账机制不能凭空恢复外部系统没有暴露的证据。

6.2 数据库写入成功，队列投递失败#

可采用事务性 Outbox：数据库事务同时保存领域对象与待发事件；投递器重试发送；消费者幂等处理。消息重复不应导致重复发布。

6.3 同时发布同一环境#

锁应覆盖相应业务边界，且执行期间可能超时或失联。只加一个 Redis 锁不足以解释所有正确性问题，还应考虑唯一约束、租约、操作版本和旧执行者写入。

可以用乐观锁限制状态迁移：

sql
UPDATE release_run
SET state = :new_state, version = version + 1
WHERE id = :id
  AND state = :expected_state
  AND version = :expected_version;

这是 SQL 设计示意。检查影响行数；更新未生效时重新读取和判断，不能继续假设自己拥有推进权。

6.4 回调乱序#

旧尝试的失败回调，不能把新尝试已经成功的状态改回失败。校验运行 ID、尝试号、资源版本及允许迁移；终态更正需要显式规则和审计。

6.5 取消与回退#

取消 API 是一个意图。Worker 可能正在执行，外部控制器也可能持续推进。需要停止后续调度、确认外部状态、收敛期望配置，再判断是否完成或需要人工处理。

6.6 多租户与凭据#

所有对象访问都需要按租户和资源授权；查询、下载日志、重试、回退都要校验。执行身份按环境授权，秘密值避免进入数据库普通字段、日志和制品。

7. 日常工作是什么样#

以下是一组教学工作事项，用于帮助理解岗位：

  • 接入一个新的代码平台，把仓库与应用自动关联。
  • 优化任务列表，让开发者看清排队与执行时间。
  • 修复重复 Webhook 导致的重复任务。
  • 为发布增加数据库变更提示与审批证据。

  • 把发布标记写入观测系统，缩短排查路径。
  • 采访接入团队，减少首次接入需要填写的配置。

平台自身也需要测试、CI/CD、可观测、值班和容量管理。平台研发会成为自己产品的使用者。

详细任务见第 13 章。先把主链跑通，再决定是否增加 GitOps、自动分析或更复杂的环境管理。

4. 八道场景题及回答要点#

题一：从一次代码提交讲到生产运行#

应覆盖触发、验证、可信制品、测试、环境配置、部署、流量、业务验证和运行反馈。每一步说清输入、成功条件和失败处理。

追问：同一个提交为什么可能产生不同制品？回答需要涉及依赖、基础镜像、构建工具和环境。

题二：CI 为什么有时很慢#

先分解排队、环境准备、依赖下载、编译、测试和报告时间，再看资源、缓存、并行和测试范围。不能直接回答“增加机器”。

追问：缓存加速后怎样防止污染与版本差异？

题三：Webhook 重复，为什么没有重复构建#

解释验签、事件 ID、业务去重键、数据库唯一约束、队列重复及执行幂等。还要允许用户显式重新运行，而不被去重逻辑永久阻止。

追问：同一 MR 的 push 与 MR 事件要合并处理吗？依据是什么？

题四：测试通过了，生产却失败了#

考虑制品与配置不同、真实数据量、路由与权限、依赖差异、资源、并发、数据库兼容，以及测试覆盖不足。先看事实再形成假设。

追问：怎样证明测试与生产使用同一内容？要说出完整摘要和配置证据。

题五：发布接口超时了，该怎么办#

先区分用户请求超时、平台任务超时和外部执行超时。查询已有任务与外部状态，利用幂等键和预先保存的关联标识对账。创建响应丢失时不能只依赖尚未取得的外部 ID；无法可靠定位时保留未知并人工核对，不能简单创建另一次发布。

追问：原 Worker 还在运行，新 Worker 接手后怎样防止双方同时推进？

题六：Pod Ready，能否判定发布成功#

还要检查目标版本、实例分布、入口路由、业务冒烟、依赖和生产指标。说明探针验证的范围，以及没有流量或指标缺失时怎样处理。

追问：把数据库是否可用放进 Liveness，可能有什么副作用？

题七：为什么不能一键回滚所有变更#

镜像、配置、数据库、消息和用户数据的恢复方式不同；新旧代码还需要兼容。解释暂停、流量切回、关闭功能、应用回退和前向修复。

追问：启用 GitOps 自动同步时，手工改集群会怎样？

题八：平台效能怎样评估#

用交付结果、稳定性、过程等待、开发体验和成本共同判断。讲清当前 DORA 定义，再根据瓶颈选择行动，不把提交数当个人产出排名。

追问：改进前后样本、服务范围和口径怎样保持可比？

3. 选择项目时怎样核对#

先看项目承担的能力，再检查：

  1. 使用的版本、开源许可证和商业功能边界。
  2. 身份、权限、执行隔离和凭据管理。
  3. 外部 API、事件、状态和恢复机制。
  4. 自己团队的环境、规模、维护成本与升级路径。
  5. 是否需要整个平台，还是只需接入其中一个模块。

本文优先介绍能力与概念，没有指定“所有团队都应该使用”的统一工具栈。正式选型还应根据实际约束单独评估。
