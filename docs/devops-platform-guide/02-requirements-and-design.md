# 02｜需求承接与技术设计

[返回阅读入口](README.md) · [下一章：开发协作](03-development-and-collaboration.md)

## 1. 阶段一：需求承接

### 输入、产出与重点

输入是业务目标，例如“用户想快速找到已经支付的订单”；产出是可验收的功能范围、优先级、依赖和交付安排。

需求中应该说明正常行为，也应该约定空结果、非法参数、权限不足和失败反馈。对平台研发而言，需求还需要关联服务、代码仓库、负责人及预期发布批次，便于后续追踪。

### 谁负责

产品或业务负责人确认用户价值、范围和验收标准。业务开发评估实现与依赖，测试提前发现边界条件，技术负责人协调风险和拆分。研发效能平台团队负责需求系统与研发流程的连接能力。

### 共用案例的需求记录

| 项目 | 教学示例 |
|---|---|
| 功能 | `GET /orders?status=paid&limit=20` |
| 身份与权限 | 使用认证上下文，只能查当前用户自己的订单 |
| 排序与分页 | 按创建时间倒序；明确相同时间的稳定排序及分页规则 |
| 参数 | `status` 使用明确枚举；`limit` 有默认值和上限 |
| 业务验收 | 正常数据、空结果、非法参数、未认证、跨用户访问均有预期 |
| 性能目标 | 在约定数据量和负载下验证；示例目标为 P95 小于 300ms |
| 服务目标 | 约定统计窗口、有效请求和成功定义；目标示例见运行态章 |
| 交付记录 | 需求编号、服务、负责人、MR、测试证据和发布记录可关联 |

这里的 300ms 只用于练习。正式目标要由业务体验、已有基线、访问规模和成本共同决定。

### 技术栈与代表性项目

需要理解 Issue、看板、工作流、权限、Webhook 和系统间 API。可以查看 [OpenProject](https://www.openproject.org/)、[Plane 开源版](https://plane.so/open-source) 和 [Gitea Issues](https://docs.gitea.com/) 如何表达任务、状态和协作。

### 核心技能

| 深度 | 应达到的能力 |
|---|---|
| 理解 | 把“做个查询”翻译成范围、边界和验收标准 |
| 使用 | 维护需求、缺陷、里程碑及代码关联 |
| 开发平台 | 实现需求与 MR／发布记录的关联，处理同步失败、权限与状态差异 |

典型开发任务：接收任务系统事件，建立需求与服务、提交和发布的关联；支持补偿同步，并保留外部系统的原始 ID，便于对账。

## 2. 阶段二：技术设计

### 输入、产出与重点

输入是明确的需求；产出是团队能够实现、测试、部署和维护的方案。

设计范围包括 API 契约、数据访问、依赖行为、兼容性、运行观测和发布方案。对一个查询接口，除了 Controller 和 SQL，还要考虑超时、分页、索引、用户隔离和失败码。

### 谁负责

业务开发或技术负责人主导方案。测试参与可验证性设计；安全团队按风险参与鉴权、数据和供应链评审；SRE 或基础设施团队协助容量与运行约束；平台团队提供标准模板和自动检查。

### 本案例需要做的设计判断

1. **API 契约**：字段、状态码、错误结构和分页语义是什么？客户端是否能识别错误？
2. **数据访问**：SQL 是否包含用户条件？扫描量是否随数据增大失控？需要新增什么索引？
3. **兼容性**：新旧代码共存时，响应和数据库结构是否都可用？
4. **依赖与资源**：数据库超时、连接池和并发上限怎样约束？请求取消后是否停止无用工作？
5. **可观测性**：请求数、失败率、延迟、慢查询和版本信息怎样关联？
6. **发布**：先部署到哪里，如何验证，小流量怎样放，什么情况下暂停？
7. **恢复**：旧版本能否读取新结构？已执行的数据变更是否需要前向修复？

设计记录可以采用简短 ADR：问题、可选方案、选择、理由、代价和回退条件。无需为小功能写冗长文档，但需要保留影响交付与运行的关键决策。

### 技术栈与代表性项目

基础是 HTTP、SQL、索引、事务、认证授权、缓存及超时处理。使用 [OpenAPI](https://www.openapis.org/what-is-openapi) 描述 HTTP API 契约，使用 [Mermaid](https://mermaid.js.org/intro/) 表达依赖和时序；跨服务行为验证可以进一步了解 [Pact](https://docs.pact.io/)。

OpenAPI 是规范，Mermaid 是图示工具，Pact 是契约测试工具。它们分别解决表达和验证的一部分问题，设计判断仍需要开发者完成。

### 核心技能

| 深度 | 应达到的能力 |
|---|---|
| 理解 | 知道功能设计会影响部署、回退和运行 |
| 使用 | 编写 API 契约、验证 SQL、补齐发布与监控要求 |
| 开发平台 | 把服务模板、契约检查、变更风险提示和审批规则接入工作流 |

典型开发任务：生成标准服务骨架，把接口契约差异检查接入 MR，并让发布单显式记录数据库变更和恢复方案。

## 3. 交接到开发前，应该能回答

- 谁确认业务验收，哪些情况必须阻断交付？
- 新旧版本会共存多久，数据库变更怎样兼容？
- 怎样知道功能在生产上工作正常？
- 哪些规则由平台自动验证，哪些仍需人工判断？

只有排期、没有可验证目标，会让后续流水线把一份“能够编译的代码”误当成“能够交付的功能”。
