# 09｜运行态、可观测性与可靠性

[返回阅读入口](README.md) · [下一章：反馈与效能](10-feedback-and-metrics.md)

## 1. 输入、产出与重点

输入是持续运行的服务、运行配置、流量、依赖和服务目标；产出是对服务状态的判断、可执行的告警、事件处置记录和改进项。

需要回答：用户是否正常使用服务，异常在哪里，怎样先恢复，怎样减少再次发生。可观测数据是判断依据；看板和工具本身不替代判断。

## 2. 谁负责

服务所属团队对服务行为与业务结果负责。SRE 按组织分工提供可靠性工程、值班和生产保障能力。平台团队提供采集接入、发布关联、告警路由和诊断入口。基础设施团队对底层平台负责。

平台后端岗位是否承担业务值班、平台自身值班，或者二者都承担，需要在面试中确认。

## 3. 从用户视角到系统内部

| 视角 | 本案例要观察什么 | 典型用途 |
|---|---|---|
| 用户／业务 | 是否能查到正确订单、权限是否正确 | 判断用户影响 |
| 服务接口 | 流量、失败率、延迟、并发 | 快速识别服务变化 |
| 应用进程 | 线程／协程、堆、GC、连接池、事件循环 | 定位应用资源问题 |
| 依赖 | SQL、连接数、锁、缓存、下游调用 | 定位外部等待和瓶颈 |
| 容器与主机 | CPU、内存、磁盘、网络、重启与调度 | 定位资源与运行环境问题 |
| 变更 | 镜像、配置、扩缩容、数据库、路由 | 形成排查假设 |

不要看到 CPU 正常就认定服务正常。数据库等待、线程池排队、网络故障和权限错误都可能影响用户。

## 4. 三类常用可观测数据

| 数据 | 擅长回答 | 要注意 |
|---|---|---|
| Metrics 指标 | 何时发生、多大范围、趋势怎样 | 标签基数、采样间隔、聚合与统计窗口 |
| Logs 日志 | 某次行为发生了什么、错误上下文是什么 | 结构化、脱敏、关联 ID、成本 |
| Traces 链路 | 一次请求经过哪些服务、耗时分布在哪里 | 传播上下文、采样、异步和缺失节点 |

实际系统还可能使用剖析等数据。本指南先掌握上述三类。

[OpenTelemetry](https://opentelemetry.io/docs/what-is-opentelemetry/)提供插桩、生成、采集与导出等能力，通常还需要后端存储、查询和展示系统。使用 OpenTelemetry 不等于已经获得完整的监控平台。

## 5. 指标、SLO 和错误预算

本文采用如下教学约定：

- **SLI**：衡量用户体验的实际指标，例如有效查询请求的成功比例。
- **SLO**：为 SLI 设定目标，例如滚动 30 天内成功比例至少 99.9%。
- **SLA**：对外的服务承诺及相应约定，需要结合合同和业务定义。
- **错误预算**：在所定目标内允许的不良事件份额。

对请求成功率 SLO，若窗口内有 100 万个有效请求、目标为 99.9%，允许的不良请求份额为 1000 次。它不是固定的一段停机分钟数。需要结合是否均匀有流量来解释影响。

服务目标相关方法参见 [Google SRE：Service Level Objectives](https://sre.google/sre-book/service-level-objectives/)。本文例子是为案例自拟的口径。

### 必须定义分母和失败

本案例可以把正常合法查询作为有效请求，把服务端错误、超时或违反约定的异常响应视作不良事件；无权限或非法参数是否进入分母，需要按业务目标明确。

如果只统计应用收到的请求，入口连接失败可能完全看不到。应结合入口指标、合成探测或用户侧证据，说明测量的覆盖范围。

## 6. 探针通过为什么仍然可能有问题

Kubernetes 中需要区分：

| 探针 | 判断目标 | 设计注意 |
|---|---|---|
| Startup | 应用是否完成启动 | 为慢启动提供合理空间 |
| Readiness | 实例是否适合接收流量 | 要与实际接流量能力匹配 |
| Liveness | 实例是否需要通过重启恢复 | 避免因共享依赖异常造成重启风暴 |

具体失败行为见 [Kubernetes Probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/)。探针可以验证必要条件，但通常不执行完整业务路径。

例如 `GET /readyz` 只检查进程与连接池状态，而 `/orders` 缺少索引导致慢查询。此时 Pod 可能 Ready，业务延迟依然很高。

## 7. 指标和日志怎样接入

建议先做一套能解释案例的最小数据：

- 接口请求数，按路由模板、状态类别等有限维度区分。
- 请求耗时直方图，支持观察尾延迟。
- 数据库操作耗时、连接池使用和等待。
- 结构化请求日志：时间、路由、状态、耗时、trace ID、版本。
- 版本与发布标记，便于把异常与变更关联。

订单 ID、用户 ID、完整 URL 通常不适合成为指标标签，会产生大量时间序列。细粒度标识应按需要放在受控日志或链路中，并考虑隐私与成本。相关建议见 [Prometheus Instrumentation](https://prometheus.io/docs/practices/instrumentation/)。

观测新旧版本时也要控制版本标签的生命周期，避免永久保留无限增长的版本组合。

### 一个延迟查询示意

假设服务已经暴露经典直方图 `order_request_duration_seconds_bucket`，含 `route` 和 `le` 标签：

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(order_request_duration_seconds_bucket{route="/orders"}[5m])
  )
)
```

它表达过去 5 分钟数据的 P95 估计。桶边界、请求样本和采集完整性会影响判断；没有数据不代表延迟是 0。分组查看版本时，应在聚合中保留对应标签。

公式与直方图行为参见 [Prometheus Histograms](https://prometheus.io/docs/practices/histograms/)。这段示例依赖应用先提供约定指标，不能直接套用任意语言默认指标名。

## 8. 告警怎样做到可行动

一条告警至少包含：

```text
发生什么、影响哪个服务和环境、从何时开始
  + 严重程度、责任人与路由
  + 指标与相关发布链接
  + 当前证据、建议检查步骤与升级路径
```

需要区分“指标超过阈值”和“应该叫醒人”。业务不可用、持续失败、预算快速消耗等问题更接近行动触发；短暂抖动或单机异常可能适合聚合、延迟判断或工单。

[Alertmanager](https://prometheus.io/docs/alerting/latest/alertmanager/)提供告警分组、路由、抑制和静默等能力。平台还需要维护负责人、服务关系和运行手册。

发布期可以调整关联与展示，但不能为了让发布页面干净而无条件屏蔽生产故障。

## 9. 一次故障处理的思路

以下是本文建议的通用排查顺序：

1. **确认影响**：哪个入口、用户范围、失败或变慢程度，是否仍在扩大。
2. **建立时间线**：何时开始，是否伴随代码、配置、数据库、流量或基础设施变更。
3. **先做可验证的止损**：暂停发布、切流、关闭功能、扩容等，需要结合原因和副作用选择。
4. **逐层缩小范围**：入口 → 服务 → 依赖 → 资源，使用指标、日志和链路互相验证。
5. **确认恢复**：从用户路径检查，比较故障前后指标，观察是否反复。
6. **记录与改进**：保留事实、证据、决策和责任明确的后续任务。

“刚发布过”只能形成相关性假设。要看异常是否集中在新版本、是否有相应调用与资源证据，以及止损后结果是否符合预期。

### 本案例：Ready，但订单查询很慢

可能的证据链：

```text
新版 /orders P95 升高
  → Trace 的数据库 span 占主要耗时
  → 数据库指标显示查询扫描量／等待异常
  → 核对 SQL、索引和执行计划
  → 暂停放量并验证止损
```

也可能是连接池过小、依赖超时、资源不足或请求构成变化。应保留备选假设，而不是看到一条慢日志就直接下结论。

## 10. 还要补哪些系统基础

对平台后端岗位，优先能使用自己的语言和 Linux 工具解释：

- 进程／线程、CPU、内存、文件描述符和连接。
- DNS、TCP、TLS、HTTP、代理与负载均衡。
- 容器日志、重启原因、资源限制、调度事件。
- 数据库索引、慢查询、连接池与锁等待。
- 超时、重试、限流、熔断与降级的作用及副作用。
- 容量预测、扩缩容、冗余和成本。

先学会针对问题找证据，再逐步补内核、网络和运行时细节。

## 11. 技术栈与代表性开源项目

| 项目 | 适用位置 |
|---|---|
| [Prometheus](https://prometheus.io/docs/introduction/overview/) | 指标采集、存储与查询 |
| [Grafana OSS](https://grafana.com/oss/) | 可视化及相关观测产品入口；区分具体组件 |
| [OpenTelemetry](https://opentelemetry.io/docs/what-is-opentelemetry/) | 插桩、采集、传播与导出 |
| [Jaeger](https://www.jaegertracing.io/docs/) | 分布式链路后端与查询 |
| [Alertmanager](https://prometheus.io/docs/alerting/latest/alertmanager/) | 告警通知编排 |

入门用 Prometheus＋Grafana 观察接口，再接入一种链路后端即可。日志后端按已有环境选择，不要求一开始搭建全部组件。

## 12. 核心技能与平台任务

| 深度 | 本章应掌握 |
|---|---|
| 理解 | 从用户结果到系统证据，SLI／SLO、数据缺失和相关性边界 |
| 使用 | 查指标、日志、Trace 和容器事件，处理一种可复现故障 |
| 开发平台 | 标准观测接入、发布关联、告警路由、诊断入口、容量与成本分析 |

平台还要监控自身：发布 API 是否可用，队列是否堆积，执行器是否失联，对账是否积压。发布平台故障时，应有清楚的受控应急操作和事后对账流程。

自测：没有收到告警，能否证明服务正常？如果发布平台显示失败，而业务已经运行新版本，你需要先查什么？
